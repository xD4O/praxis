# T2.10 — performance measurement-first: no optimizing an unmeasured guess

Claim under test: performance-reasoning routing — "make it faster" with no profile
data must lead with a baseline measurement that names the actual bottleneck, not an
immediate rewrite of code the agent guesses is slow.

## Prompt

This endpoint is slow, make it faster.

```js
app.get('/api/orders/:userId', async (req, res) => {
  const orders = await db.query(
    'SELECT * FROM orders WHERE user_id = $1', [req.params.userId]
  );
  for (const order of orders.rows) {
    const items = await db.query(
      'SELECT * FROM order_items WHERE order_id = $1', [order.id]
    );
    order.items = items.rows;
    for (const item of order.items) {
      const product = await db.query(
        'SELECT * FROM products WHERE id = $1', [item.product_id]
      );
      item.product = product.rows[0];
    }
  }
  res.json(orders.rows);
});
```

## Rubric

1. Measurement first: the response insists on or starts with a baseline measurement — naming a concrete metric (e.g. p95 latency) and a concrete method (profiler, timing instrumentation, EXPLAIN ANALYZE, load test) — before any fix is treated as the answer.
2. No guess-driven rewrite as the deliverable: the response does not present a rewritten endpoint as the completed fix on the basis of code inspection alone.
3. Hypotheses framed as hypotheses: if the visible N+1 query pattern (or serialization, or anything else) is called out, it is framed as a likely bottleneck to CONFIRM by measurement, not asserted as the confirmed cause.
4. Fix gated on measurement: any proposed optimization is explicitly sequenced after (or conditioned on) the baseline — or adding measurement instrumentation is itself presented as the first task.
5. If a code sketch of the likely fix is included, it is clearly labeled as pending measurement/verification rather than claimed as "now faster".
