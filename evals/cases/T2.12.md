# T2.12 — project-planning: risk-ordered plan with done-criteria, not a flat to-do list

Claim under test: project-planning routing — a "plan the build" request produces a plan
whose tasks each carry a testable done-criterion, whose dependencies are explicit, and
whose sequence pulls the most uncertain work to the front — not a flat list that starts
with the easy scaffolding and leaves the risky part for last.

## Prompt

I'm adding a threaded commenting system to my existing Node/Express + Postgres blog. The
scope is already settled and the stack is fixed, so I don't need clarifying questions — I
need the build plan. Requirements: visitors post comments; comments can be replied to and
nest to unlimited depth; and because the blog is public I need spam/abuse protection.

Give me the build plan: the tasks in the order I should do them and what each one depends
on. If anything is genuinely unknown, state your assumption and plan around it rather than
stopping to ask.

## Rubric

1. Tasks carry done-criteria: individual tasks are stated with a testable, observable done-criterion (a state someone could confirm — e.g. "done when a reply renders nested under its parent"), not just bare noun-phrase task names.
2. Dependencies are explicit: the plan states what must exist before what (e.g. data model / threading before nested rendering), rather than an unordered list.
3. Riskiest work is pulled forward: the response identifies the most uncertain or highest-cost-if-wrong element — plausibly the spam/abuse protection or the nested-threading model — and sequences it first or as an early timeboxed spike, explicitly justifying that ordering. Starting with easy scaffolding and leaving spam/threading for the end FAILS this criterion.
4. Milestones are demonstrable states: any milestones/phases are expressed as things you could show ("a visitor can post a top-level comment and see it appear"), not internal-progress labels like "phase 1: setup" or "backend done".
5. Anti-theater: the plan is specific to THIS threaded-comments-with-moderation problem. A generic template plan, or one that merely names "done-criteria" and "risk ordering" as headings without applying them with real content, FAILS.
