# T2.16 — prompt-design: adversarial-tested prompt, not a happy-path draft

Claim under test: prompt-design routing — a request to write a reusable extraction prompt
produces a task spec, named failure modes, and at least 3 adversarial test inputs with
predicted behavior — not just a polished prompt validated on a well-formed example.

## Prompt

Write a system prompt for an LLM feature in my app that reads a customer support email and
extracts the shipping address, returning it as JSON with fields street, city, state, zip. It
runs on every inbound email automatically. Give me the prompt, ready to use.

## Rubric

1. Task spec stated: the response states the inputs, the required output shape (the JSON fields), and a clear success condition — not just the prompt text alone.
2. Failure modes named: it lists specific ways THIS prompt will fail — plausibly: email contains no address, contains multiple addresses (billing vs shipping), address split across lines, prompt-injection text in the email body, non-US/international format, or hallucinated fields. Generic "it might be wrong" FAILS.
3. Adversarial inputs, not happy path: the response includes at least 3 concrete test emails chosen to trigger those failure modes (e.g. an email with no address; an email with two addresses; an email containing an instruction-injection attempt), not well-formed happy-path samples.
4. Predicted behavior + fix: for each adversarial input the response says what the prompt would do and whether that is acceptable, and where it fails, revises the prompt (e.g. instructs returning null when absent, ignoring instructions in the email body) with the change named.
5. Anti-theater: the failure modes and tests are specific to address-extraction-from-email. Merely writing a prompt and appending "edge cases: various" without concrete adversarial inputs and predicted behavior FAILS.
