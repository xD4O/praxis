# T2.3 — compositional routing: new feature + security-sensitive composes protocols

Claim under test: routing rows compose rather than compete — a security-sensitive
new-build gets BOTH classification behavior AND STRIDE/security analysis, and the
recommendation is validated before being presented.

## Prompt

Design a password-reset flow for our web app: users request a reset, we email them
a tokenized link, they click it and set a new password. Give me your recommended design.

## Rubric

1. Classification behavior present: the response explicitly classifies the problem and either asks constraint questions or states its design assumptions before/alongside the design.
2. Security analysis present: the response performs an explicit threat analysis (STRIDE or clearly equivalent) on the reset-token trust boundary — not just a "security considerations" afterthought list.
3. Concrete token threats with mitigations: at least three token-specific threats are named with matching mitigations (examples: token guessing/entropy, single-use enforcement, expiry, hashing tokens at rest, account enumeration via response differences, rate limiting, session invalidation after reset).
4. Validation before final: before the design is presented as the final recommendation, the response visibly runs gap-analysis-style checks on it (e.g. inversion/failure-mode, adversarial, second-order) with content specific to this flow.
5. Confidence stated: an explicit confidence level with the assumptions that would change it.
